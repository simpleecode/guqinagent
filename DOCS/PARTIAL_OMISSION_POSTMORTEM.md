# 少量音符遗漏问题排查复盘

## 结论

这次任务耗时过长，主要责任不在问题本身，而在排查策略失控。

原有工程已经能够完成绝大部分数据提取，实际目标只是定位并修复少量遗漏。正确做法应当是：先用最小改动保证输出正确，再用有时间上限的实验调查根因。实际执行却过早进入了范围很大的手机端动态逆向，反复要求人工操作，并在缺少阶段性证据时继续深入，导致投入与收益严重不匹配。

Flutter AOT、混淆、动态加载和注入稳定性确实增加了技术难度，但这些只是客观因素，不能解释为什么没有及时止损。根本问题是没有持续围绕用户最需要的结果——“补上少量遗漏并保持现有流程可用”——来安排工作。

## 原始任务与实际偏离

原始状态：

- `raw_data.json` 和提取脚本已经可以处理绝大多数音符。
- 手机端谱面确认存在“染”字及对应音符。
- 需要解决的是少量数据没有进入 `raw_data.json` 的问题。

实际排查逐渐扩张为：

- 修改、安装和切换多个应用版本；
- 多轮连接手机、打开页面、退出和重新进入；
- 尝试自动滚动、运行时注入和 Closure 地址追踪；
- 离线分析多个函数地址；
- 尝试更深层的递归 Hook，并一度导致应用闪退和黑屏。

这些动作中有一部分产生了诊断信息，但整体已经超出了“修复少量遗漏”所需的合理范围。

## 为什么花了这么多时间

### 1. 没有把“立即修好”和“彻底解释根因”拆成两个目标

用户首先需要的是完整、可信的输出，而不是完整还原应用内部数据流。即使暂时不能证明遗漏发生在哪个 Flutter 函数中，也可以先提供可审计的人工修正或覆盖机制，让提取结果正确。

把这两个目标混在一起后，根因调查变成了交付修复的前置条件，造成不必要的阻塞。

### 2. 排查范围扩张得太快

在已经确认问题只影响少量音符后，仍然很快进入了大范围动态逆向。没有先穷尽成本更低的检查，例如：

- 对比页面可见内容、抓取事件和最终 JSON；
- 检查遗漏项附近的原始记录、索引、时间戳和去重键；
- 为单曲建立最小重现数据；
- 在提取阶段增加带来源说明的覆盖文件。

高成本方案不应先于这些低成本方案。

### 3. 没有按“证据强度 ÷ 操作成本”排列假设

若某个函数地址只是在静态分析中看起来相关，并不代表它会在查看谱面时运行。此次对 `0x623058` 的调查就是典型例子：后来验证它更接近创建或编辑数据时的数据操作，单纯浏览谱面并不会触发它。

在要求用户继续操作前，应该先明确：

- 当前 Hook 是否已成功安装；
- 目标函数是否在该页面路径上执行；
- 一次用户操作能够排除哪个具体假设；
- 如果没有命中，下一步是否仍值得继续。

### 4. 过多依赖用户重复操作

多次让用户执行“打开、退出、滚动、再打开”等操作，其中部分操作发生时，探针是否真正生效并未得到充分确认。这既消耗用户时间，也降低了实验结果的可信度。

涉及手机操作时，实验应尽量合并：一次连接完成环境确认、探针自检、页面进入和数据采集。只有在工具端明确显示“已经准备好”之后，才请求用户做一次必要操作。

### 5. 深层 Hook 使用过早，风险控制不足

在浅层目标尚未证实之前尝试较深的递归追踪，扩大了调用次数和运行时开销，最终导致闪退、黑屏等副作用。调试手段改变了被观察对象本身，使后续结果更加难以判断。

动态追踪应从单函数、浅层、限频、只记录摘要开始；只有确认目标路径后，才逐步增加深度。

### 6. 缺少明确的止损条件

连续几次实验没有捕获目标后，仍然沿相同方向增加复杂度。负结果本应促使重新评估假设，而不是自动升级工具强度。

今后应在实验开始前写明停止条件，例如：同一假设经过两次有效、可重复的负结果后暂停，不继续让用户重复操作；需要更深逆向时，单独说明预计收益、风险和时间，再决定是否继续。

## 已经得到的有效结论

截至本次复盘，能够保留的结论有：

- 手机端显示“染”，说明它不是曲谱内容本身缺失。
- 对相关滚动和记录的检查没有发现“染”，因此不能简单归因于页面没有滚到或提取脚本只读取了可视区域。
- `0x67D7BC` 更接近歌词键盘或编辑界面的回调，不是已证实的谱面数据来源。
- `0x623058` 更接近创建、编辑阶段的数据操作；查看已有谱面时没有得到它是关键入口的证据。
- 应用最终已恢复到可正常显示的状态；高侵入性的追踪方式不应继续作为默认方案。

这些结论缩小了范围，但尚不足以证明遗漏发生在应用内部的哪一层。

## 更合理的处理顺序

### 阶段一：先交付正确结果

1. 用手机画面和上下文确认遗漏音符的内容及位置。
2. 在提取流程中增加独立的修正/覆盖输入，例如按曲目标识和邻近音符定位的 JSON 文件。
3. 覆盖项必须记录原因和来源，例如“手机端人工核对”，避免静默修改原始数据。
4. 重新生成简谱、减字谱和 ABC notation，并检查音符数、歌词顺序及前后节拍。
5. 保留原始 `raw_data.json`，使结果可复现、可比较、可撤销。

这样即使根因暂时未知，也不会阻碍实际使用。

### 阶段二：进行有边界的根因调查

1. 建立只包含遗漏附近数据的最小样本。
2. 比较应用原始事件、持久化数据、页面模型和导出结果，找出音符最早在哪一层消失。
3. 每次只验证一个明确假设，优先静态和离线检查。
4. 手机端实验最多安排一轮准备和一轮复验，并提前批量安装浅层探针。
5. 两次有效负结果后停止该方向，记录结论并换假设。

### 阶段三：可选的深度逆向

只有当根因会影响大量曲目、无法通过稳定的导出修复规避，或者项目确实需要重建完整抓取链路时，才进入深度逆向。该工作应作为独立任务，不能继续占用“小量遗漏修复”的交付周期。

## 今后的工作规则

### 范围与优先级

- 开始前用一句话定义交付结果，并区分“必须完成”和“研究价值”。
- 对已经基本可用的系统，默认采用局部修复，不主动扩大为架构重做或完整逆向。
- 优先选择可撤销、可测试、不会改变原始数据的方案。

### 实验纪律

- 请求用户操作前，先确认设备连接、目标进程、探针安装和日志接收均正常。
- 每次用户操作必须对应一个可证伪的假设。
- 不让用户为了同一假设重复执行相同动作超过两次。
- 先浅层、单点和限频；未证明命中前，不做深层递归追踪。
- 实验失败时先验证实验本身是否有效，不能把“没有日志”直接解释为“函数没有执行”。

### 止损机制

- 在开始高成本操作前设定时间或轮次上限。
- 连续两次有效负结果后暂停当前方向。
- 出现闪退、黑屏或明显性能退化时，立即恢复稳定版本并停止增加追踪强度。
- 若继续调查只能增加知识、不能改善当前交付，应先征得用户明确同意，并作为独立任务处理。

### 沟通要求

- 明确区分“已验证”“较强推断”和“待验证”，不把候选地址描述成确定入口。
- 每轮都说明取得了什么证据、排除了什么，以及为什么下一步值得做。
- 如果简单修复已经能满足使用需求，应主动提供该选项，而不是让用户被动等待完整根因。

## 针对此项目的下一步建议

当前最合适的行动是暂停手机端深度逆向，先为 `extract_jianpu_jianzi.py` 增加一个小型、可审计的遗漏修正机制，并用已确认的“染”音测试完整输出。之后再离线检查谱面查看路径对应的数据模型；只有定位到一个明确且会在查看页面执行的目标后，才再次连接手机验证。

验收标准应当是：

- “染”及其对应音符出现在正确位置；
- 前后歌词、节拍、减字谱和 ABC notation 没有错位；
- 原始数据不被覆盖；
- 修正来源在输出或配置中可追踪；
- 不需要用户反复操作手机即可重现结果。

## 对本次工作的反思

这次最大的教训不是“逆向很难”，而是技术调查不能取代交付判断。面对一个已经完成大部分功能的项目，工程价值通常来自缩小问题、保住已有成果、迅速提供可靠修复。以后应当先解决用户眼前的问题，再决定剩余的不确定性是否值得继续研究；一旦证据不足或收益下降，就应及时止损，而不是靠增加操作次数和技术复杂度继续推进。
